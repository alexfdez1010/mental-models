A report announces that search method AB beats method AC. Before choosing a winner, open the test protocol. Which tasks were included? How were they weighted? What did each method observe, and how much searching was allowed?

A **benchmark** is a specified set of test problems and a procedure for scoring methods on them. This workshop audits a complete, constructed benchmark. The arithmetic is exact within that small world; it is not a measured result about real software or a promise about an arbitrary future batch of jobs.

## Fix the protocol before reading the winner

<MCQ client:visible pretest question="Two reports disagree about the best search method. What must match before their scores are directly comparable?"
  options={[
    { text: 'The task population, scoring rule, information and evaluation budget.', correct: true },
    { text: 'Only the method names, regardless of the tasks or resources used.' },
    { text: 'Only the largest score printed in either report’s summary.' }
  ]}
  explanation="A method name does not define a comparison. Changing tasks, information, score or allowed evaluations can change what the result means."
/>

Imagine a preview-export task with three available presets, **A, B and C**. Testing a preset returns a reward of **0 or 1**, with the larger reward preferred. A **function** here is simply a fixed assignment of one reward to each preset. For example, **001** means A returns 0, B returns 0 and C returns 1.

The following rules define the initial benchmark:

| Protocol field | Declared rule |
|---|---|
| Possible tasks | All eight binary assignments to A, B and C |
| Task weights | Each assignment has weight 1/8 |
| Observations | A method learns only the rewards of presets it has tested |
| Tests | No noise, changing rewards or repeated queries |
| Method AB | Query A, then B |
| Method AC | Query A, then C |
| Budget | Exactly two distinct queries per method, even if the first returns 1 |
| Raw score | The highest reward among that method's two observed values |

A **query**, or evaluation, is one test revealing a preset's reward. These methods have fixed orders. Neither can read an unqueried value from the auditor's table. Their budget is an exact count, not permission to stop early after a promising result.

In the static finite setting of Wolpert and Macready's **1997** result, a uniform average over all objective functions gives the same distribution of observed reward sequences for methods using the same number of distinct evaluations. Applying the same score to those sequences therefore gives equal averages. This is a conditional statement about a search model, not a theorem about every kind of method, runtime or everyday choice. [Primary paper](https://faculty.cc.gatech.edu/~isbell/reading/papers/nfl-optimization.pdf)

## Reconstruct the score on every task

<MCQ client:visible pretest question="A method observes only zero rewards. Must it have failed to observe a global maximum?"
  options={[
    { text: 'No; if the whole function is zero, an observed zero is a global maximum.', correct: true },
    { text: 'Yes; zero can never be the largest value in a finite function.' },
    { text: 'Yes; a queried value is a maximum only if every input was tested.' }
  ]}
  explanation="A global maximum is the highest value anywhere in that task. Its value can be zero. Finding a one and observing a global maximum are different success criteria."
/>

Read each row as one complete function. The last columns are **max(A,B)** and **max(A,C)**: keep the larger of the two values each method queried.

| Function ABC | A | B | C | AB observed score | AC observed score |
|---|---:|---:|---:|---:|---:|
| 000 | 0 | 0 | 0 | 0 | 0 |
| 001 | 0 | 0 | 1 | 0 | 1 |
| 010 | 0 | 1 | 0 | 1 | 0 |
| 011 | 0 | 1 | 1 | 1 | 1 |
| 100 | 1 | 0 | 0 | 1 | 1 |
| 101 | 1 | 0 | 1 | 1 | 1 |
| 110 | 1 | 1 | 0 | 1 | 1 |
| 111 | 1 | 1 | 1 | 1 | 1 |
| Sum of scores | | | | 6 | 6 |

On **001**, AB observes 0 and 0; AC observes 0 and 1. AC wins that row. On **010**, AB wins instead. The remaining rows tie. Each score column sums to **6**, so each weighted mean is **6/8 = 3/4 = 0.75**.

Because our scores are only 0 or 1, their mean also equals the probability of **observing at least one 1** under the stipulated weights. That numerical coincidence depends on this binary score definition.

It is **not** the probability of observing a global maximum. AB misses a global maximum only on **001**; AC misses it only on **010**. Both therefore observe a global maximum on **7/8** of these functions, including **000**, where the global maximum is 0. The raw-score mean remains **6/8**. Report the metric you actually calculated.

These are all possible functions in this defined toy world, not eight sampled jobs. A future batch need not contain each function once. Exact enumeration establishes the stated weighted average; it does not remove randomness from a future sequence or establish real-world task frequencies.

## Change the population before choosing a method

<MCQ client:visible pretest question="A future task population is narrower than all binary functions. What follows automatically?"
  options={[

    { text: 'Every restriction must make the two methods have different means.' },
    { text: 'The method that won one selected row must win every future task.' }
  ]}
  explanation="A restriction can change the comparison, but does not guarantee a difference. Specify which functions remain and how likely each is."
/>

Now a contract known **before method selection** specifies **C always returns 0**. The four remaining functions each have weight **1/4**. AB and AC still follow their fixed two-query protocols; AC uses a query on C even though that value is now known from the contract.

| Permitted function ABC | Weight | AB observed score | AC observed score |
|---|---:|---:|---:|
| 000 | 1/4 | 0 | 0 |
| 010 | 1/4 | 1 | 0 |
| 100 | 1/4 | 1 | 1 |
| 110 | 1/4 | 1 | 1 |
| Sum of scores | | 3 | 2 |

AB's mean is **3/4 = 0.75**, while AC's is **2/4 = 0.5**. Same metric and query count, different task law. Under this law AB has an advantage over AC. That is a comparison of these protocols on this population, not a proof that AB is optimal among all possible methods.

Nor does every restriction create an advantage. If only **000 and 111** are possible, each with weight **1/2**, every two-query method observes either two zeros or two ones. Every such method has mean observed score **1/2**. This restricted population still gives a tie. You can verify it without a larger theorem: both functions are constant across A, B and C.

A flattering subset chosen **after** seeing the results does not show that future tasks follow its law. If a report keeps only the four C-zero rows to advertise AB, ask for an independent reason those rows describe the intended workload. The contract supplied that reason in our hypothetical case; the table alone would not.

## Add costs without changing the question silently

<MCQ client:visible pretest question="One method has a higher raw-score mean but uses more queries. Does that alone make it the better costly decision?"
  options={[
    { text: 'No; the objective must say how extra score and evaluation cost are valued.', correct: true },
    { text: 'Yes; query costs cannot affect a ranking by expected net benefit.' },
    { text: 'Yes; the fixed-query theorem compares every resource budget at once.' }
  ]}
  explanation="A raw-score comparison and a net-benefit comparison have different objectives. A theorem at a fixed query count does not equalise candidates using different counts."
/>

Return to **all eight functions with weight 1/8 each**. Add a separate, fictional value scale: a raw score of **1 earns 10 planning credits (cr)**; a score of **0 earns 0**. Each evaluation costs **c credits**. Our objective is the highest **expected net benefit**, meaning the weighted average benefit after paying every required evaluation cost.

Compare only these declared candidates:

| Candidate | Required evaluations | Expected gross benefit before evaluation costs |
|---|---:|---:|
| AB | 2 | 10 × 6/8 = 7.5 credits |
| A only | 1 | 10 × 4/8 = 5 credits |
| Abstain | 0 | A separately specified outside payoff of 0 credits |

Abstention is an outside option, not a claim that the maximum of an empty observation set is zero. AB still performs both queries even when A already returns 1. A only always performs its one query.

Since each protocol's query count is fixed, its total cost is the same on every function. Thus AB's expected net is **7.5 − 2c**; A only gives **5 − c**; abstention gives **0**. At cost **3**, AB gives **1.5**, A only gives **2**, and abstention gives **0**. The larger gross score does not win the net comparison.

| Cost per evaluation in credits | AB net | A only net | Abstain | Highest among these candidates |
|---:|---:|---:|---:|---|
| 1 | 5.5 | 4 | 0 | AB |
| 2.5 | 2.5 | 2.5 | 0 | AB and A only tie |
| 3 | 1.5 | 2 | 0 | A only |
| 5 | −2.5 | 0 | 0 | A only and abstention tie |
| 6 | −4.5 | −1 | 0 | Abstain |

/>

The two ties have different meanings. **AB − A only = 2.5 − c**, so their net values meet at **c = 2.5**. **A only − abstention = 5 − c**, so those meet at **c = 5**. At that second tie, AB is already below both. Distinguish a pairwise crossing from the highest value among all listed candidates.

Below cost **2.5**, AB leads this set; between **2.5 and 5**, A only leads; above **5**, abstention leads. The boundary points retain the stated ties. Other protocols, including rules whose query counts depend on observed values, require their own accounts. None has been proved inferior by this table.

Use this audit when a report compares a long, expensive search with a short one, or changes from raw score to value after costs. Different query counts and an added utility scale are reasons to rebuild the comparison, not violations of the fixed-query tie.

## Audit a new population independently

A new workload is specified **before selection**: **B always returns 0**, and the four compatible functions have equal weight. Keep the same AB and AC methods, the same exact two-query budget and the **raw observed-score objective**. This is a new task law, not the earlier credit-cost question.

| New permitted function ABC | A | B | C |
|---|---:|---:|---:|
| 000 | 0 | 0 | 0 |
| 001 | 0 | 0 | 1 |
| 100 | 1 | 0 | 0 |
| 101 | 1 | 0 | 1 |

Calculate both score columns yourself. Does the earlier AB advantage transfer? Also check the global-maximum criterion: does a raw score of zero always count as a failure there?

For global-maximum success, add the all-zero row. AB observes a global maximum on **3/4** of these functions and AC on **4/4**. Those are different numbers from their observed-one rates. No function disappeared merely because all its rewards were zero.

A defensible report names the population and its weights, the information each method had, its query protocol and the metric. To extend a benchmark result to a real workload, obtain evidence that the workload and costs match those assumptions. Fresh tasks not used to select the favourable benchmark can help assess that extension; the toy enumeration alone cannot establish it.
