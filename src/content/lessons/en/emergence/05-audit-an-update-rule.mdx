Two implementations receive the same four values and the same instruction: copy the local majority. One keeps alternating forever. Another reaches agreement in a single sweep. Before blaming the code, check what “update” meant.

This is a constructed model you can audit completely. It extends the course’s micro-to-macro idea: knowing the local calculation is useful, but the connections, starting configuration and timing also belong in the model. Nothing here estimates how real people, birds or machines behave.

A **configuration** is the ordered list of all current node values. Our four labelled nodes form the ring A–B–C–D–A. Each holds either 0 or 1. The string `0101` means A=0, B=1, C=0, D=1; keep its leading zero. Neither value is good, bad, true or false. They are just two possible states.

A node’s **neighbourhood** consists of its left neighbour, itself and its right neighbour. For A that is D,A,B; for B it is A,B,C. C reads B,C,D, and D reads C,D,A. Including the node itself matters: the vote has three inputs, so no tie is possible.

The **local rule** returns 1 when at least two of those three inputs are 1, and otherwise returns 0. Here is its complete truth table:

The remaining specifications form the model card:

- The four positions and their ring connections are fixed.
- There is no noise, outside input, random choice or change of local rule in the main comparison.
- A **protocol** specifies when values are read and written, and in which order nodes update.
- A simultaneous **round** updates every node from one preceding snapshot. A sequential **sweep** updates each node once in a declared order, reading the latest values.
- These events are counting units within a model. No duration in seconds is assumed, and one node update is not one whole simultaneous round.

### When this specification helps

Use a model card when two simulations disagree, when you reproduce a result, or when a proposed intervention changes one part of a rule. It prevents an implementation detail from silently becoming an assumption about the process being modelled.

## Read together, then write

A **simultaneous update** reads an immutable copy of the preceding configuration. Calculate all proposals first; commit them together. We begin at `0101`.

No proposal uses an earlier proposal from the same round. Reading the last column in ABCD order gives `1010`. At the next round, every node again sees two neighbours opposite to itself, so every value flips back: `0101 → 1010 → 0101`.

A **fixed configuration** is one that all applicable local updates leave unchanged. A **cycle** repeats configurations after complete rounds. This alternating pair has a cycle of length 2. Because the rule is deterministic and the same complete configuration recurs at the same phase, continuing repeats the same two configurations. A fixed state has period one mathematically; we label it fixed rather than adding a redundant cycle warning.

Count the ones: there are 2 before and 2 after every round, even though all four nodes change value. An unchanged total can conceal a changing arrangement.

### When to use snapshot reads

Use this protocol when the model explicitly assumes a common preceding snapshot. A loop can still calculate those proposals one by one, provided it reads the copy and writes to separate storage. The order of calculating proposals then does not change the committed round. Updating the same storage immediately is a different protocol.

### When order matters

If later calculations can read earlier writes, order can matter. The two sweeps establish that possibility for this rule and start. They do not prove that every order, initial state or asynchronous protocol behaves differently. Check the declared alternatives rather than treating one convenient schedule as a neutral default.

## Check the whole finite catalogue

Trying two orders finds a counterexample to order-independence. It does not establish what every possible start or order does. This system is small enough to enumerate: each of four positions has two values, so there are $2^4=16$ configurations. Updating each node once gives $4!=24$ complete orders, or $16\times24=384$ start/order pairs.

You can check the classification without guessing:

- With no ones or four ones, every local majority preserves its value: `0000` and `1111` are fixed.
- With one one, that node has two zero neighbours and disappears; every zero sees at most one one. Three ones give the complementary result. These eight starts reach unanimity in one simultaneous round.
- With two adjacent ones, each node has at least one neighbour matching itself. The four arrangements `0011,0110,1001,1100` are mixed fixed configurations.
- With two alternating ones, both neighbours oppose every node. Those two configurations flip into each other.

That accounts for all sixteen starts: 2+8+4+2. There are six fixed configurations, not six unanimous configurations. In particular `0011` and `0101` have the same count of ones and different dynamics. The arrangement carries information that the count discarded.

For an alternating start, the first updated node flips to match its neighbours. Its immediate neighbours then have a matching neighbour and keep their values; the opposite node flips when its turn arrives. ### When enumeration is enough

For a small state space, an exhaustive check can support a bounded guarantee. For a larger space, a few successful runs are samples of runs, not exhaustive proof. Record which initial states, schedules and boundary conditions were actually checked.

## Pin a node and test the objective

Suppose your objective is to remove the alternating cycle. A proposed intervention holds A at 0 permanently, while B,C,D continue simultaneous majority updates. Restrict the legal starts to the eight strings beginning with 0. A is already zero at the start; this intervention changes its rule throughout, rather than flipping it once and returning to the old model.

A second stakeholder wants a stronger result: all four values must eventually be zero. Before opening the solution, decide whether the intervention meets both objectives. Work from `0101` and `0111`, then consider whether either example alone settles all eight starts.

### When to test a stronger objective

After an intervention, ask which property it actually changes. Eliminating oscillation, reaching a fixed state, reaching agreement and reaching a particular value are different objectives. An intervention can satisfy one and fail another. Persistent rules, legal starting conditions and the observation window must stay explicit when the case changes.

## Use the audit beyond this ring

A report says: “The values stopped changing, so the model works.” Ask what was recorded. If the report compares only the values before and after B in an ABCD sweep, `1101 → 1101` is insufficient: C has not yet updated. A record showing all four applicable proposals equal to the current values would establish fixedness at that configuration. A repeated complete-round configuration at the same phase can establish periodic continuation under an unchanged deterministic rule. Neither observation by itself validates the rule for a real process.

For a proposed implementation, keep the initial data fixed and log the values each node reads. From `0101`, B reads A=0 in a simultaneous round but A=1 after A’s immediate write in the ABCD sweep. That specific read discriminates the two protocols; a final picture alone may not. Agreement with one trace is a useful check, while agreement over the complete finite catalogue proves equivalence only over that declared domain.

Blok and Bergersen’s study of a different cellular-automaton model distinguishes update schemes and recommends checking relevant alternatives. The NetLogo manual likewise specifies serial versus interleaved execution and fixed ordered lists. Those sources support making timing explicit. They do not turn this ring into a measured model of a crowd or machine. [Blok and Bergersen’s author manuscript](https://www.cs.ubc.ca/~rikblok/research/published/blok99.pdf), [NetLogo Programming Guide](https://docs.netlogo.org/programming.html).
