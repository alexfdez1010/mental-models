The festival's ticket label should read **AB-CD**. The final preview reads **ABCD**. Your colleague says the exporter removed the hyphen. You suspect the badge formatter. Both of you can point at the same broken label and announce that the evidence agrees with you. A productive meeting, by the usual standards of meetings.

This workshop turns the disagreement into a **prediction matrix**: a table of what each explanation predicts under each test. The ticket system and every result below are invented. You need no knowledge of a particular file format or software product; the mechanism is fully specified here.

## State alternatives that could actually differ

Our fictional system has two stages. An **exporter** writes a label string. A **formatter** reads that string and produces the displayed label. The current version of either stage might contain a setting that deletes hyphens. A stage with that setting off preserves the input exactly. Deleting a hyphen twice has the same visible result as deleting it once.

For this bounded model, each setting is fixed during the investigation and either on or off. The model is **deterministic**: the same input through an unchanged path always produces the same output. There are four candidate explanations:

| Candidate | Exporter deletes hyphens | Formatter deletes hyphens |
|---|---|---|
| Exporter only | Yes | No |
| Formatter only | No | Yes |
| Both | Yes | Yes |
| Neither | No | No |

This list is exhaustive **for these two binary settings**. It is not a claim that real label systems have only two possible faults. A stale preview, a different transformation or a bad inspection tool would require checking the setup or adding another model.

The ordinary end-to-end result, **ABCD**, fits the first three candidates. It conflicts with “neither” only if the input was really AB-CD, the observation is accurate and nothing outside the stated mechanisms changed it. Naming a candidate and recording those assumptions are separate jobs.

### When to use the matrix

Use it when several explanations fit the same observation. Give each candidate an operational meaning: what it does, when it does it and what it predicts. Include combinations when causes can coexist. “Something is wrong” may describe the situation accurately, but it cannot locate a cause.

## Compare predictions before choosing a test result to like

<MCQ
  client:visible
  pretest
  question="Suppose the isolated exporter test produces the result your exporter-only explanation predicted. Can that result still teach you something?"
  options={[
    { text: 'No, a confirming result is always uninformative.' },
    { text: 'Yes, if competing explanations predicted a different result under the same valid setup.', correct: true },
    { text: 'Yes, it proves your explanation is the only possible one.' }
  ]}
  explanation="Diagnostic value depends on the rival predictions. A result can support your expectation while excluding some rivals, yet leave another explanation compatible."
/>

An observation is **diagnostic between candidates** when they predict different outcomes for it. Ask what each candidate expects under the same test. Whether you personally hope for the outcome is a different question.

We have trusted substitutes for both stages. The trusted exporter writes AB-CD exactly; the trusted formatter preserves exactly the string supplied to it. They do not restore a hyphen already lost. Every run starts with a fresh input and clears the previous preview. The observation tool is independent of the formatter and compares the output characters with the intended input.

Prepare these four paths:

| Path | Exporter | Formatter | What the path checks |
|---|---|---|---|
| Ordinary path | Current | Current | Reproduce the reported symptom |
| Exporter isolation | Current | Trusted | Observe the exporter without the current formatter |
| Formatter isolation | Trusted | Current | Observe the formatter with a known preserved input |
| Trusted control | Trusted | Trusted | Check that the reference path and readout preserve the hyphen |

Now fill the predictions **before looking at the isolation results**. “Lost” means the output is ABCD; “kept” means it is AB-CD.

| Candidate | Ordinary path | Exporter isolation | Formatter isolation | Trusted control |
|---|---|---|---|---|
| Exporter only | Lost | Lost | Kept | Kept |
| Formatter only | Lost | Kept | Lost | Kept |
| Both | Lost | Lost | Lost | Kept |
| Neither | Kept | Kept | Kept | Kept |

Repeating the ordinary path and seeing “lost” again cannot separate the first three candidates: they share that prediction. Such repetitions can check stability, but agreement on the outcome gives them no new separating power. The isolated paths do separate them.

Klayman and Ha distinguish a positive testing strategy from a general tendency to favour a conclusion. They show that its usefulness depends on the task; seeking an expected outcome is not automatically a bad test. The prediction table makes that distinction concrete here. [Klayman and Ha's original paper](https://pages.ucsd.edu/~mckenzie/KlaymanHaPsychReview1987.pdf)

### The practical test of a test

Say aloud which candidates would become less credible under each possible outcome. If every candidate predicts the same thing, that result cannot choose among them within this model. If the candidates differ, a result you expected can still be useful. Emotional discomfort is not a measurement of diagnostic value.

## Declare how you will revise each candidate

<MCQ
  client:visible
  pretest
  question="What makes a revision plan more useful than writing 'we will be objective'?"
  options={[
    { text: 'It states observations, validity checks and their consequences for every candidate before the new results arrive.', correct: true },
    { text: 'It promises to retain the favoured explanation regardless of the result.' },
    { text: 'It specifies what would challenge the rival but leaves your own prediction flexible.' }
  ]}
  explanation="A specific, symmetric plan makes later changes visible. A general intention does not fix what will count as a contradiction or an invalid test."
/>

Save a dated note before the isolation runs. Record the symptom already seen, the candidate table, exact inputs, component versions, test order, readout rule and the conditions below. Someone else should be able to reproduce the procedure without guessing what “basically the same label” means.

1. Run the trusted control before and after the isolation paths. If it loses the hyphen, pause interpretation and investigate the reference path or observation tool. Do not award the result to your favourite fault.
2. If a valid isolation path loses the hyphen, retain candidates with that stage active and reject the candidates predicting preservation under the stated deterministic assumptions.
3. If a valid isolation path keeps the hyphen, retain candidates with that stage inactive and reject the candidates predicting deletion.
4. If repeated runs of an unchanged path disagree, the fixed-setting, deterministic model is not adequate for that run. Record the disagreement, check conditions and plan a test of a revised explanation.
5. Keep every result in the log. Apply the same validity standard whether the result agrees with your preferred candidate or threatens it.

This is a practical revision contract, not a formal scientific registration. The same transparency principle underlies preregistration: distinguish what was planned from what was learned after seeing data. Plans can change; preserve the original and explain the change. The Center for Open Science explicitly allows conditional plans and documented deviations. [COS guidance on preregistration and changes](https://www.cos.io/initiatives/prereg)

### When an exception is legitimate

A failed control can be a genuine reason to withhold a conclusion. A new explanation can be a genuine discovery. The safeguard is to name the problem, retain the earlier record and test the revised account with a new observation. Secretly changing the rules only when your candidate loses is the asymmetric scrutiny this course warns about.

## Read the whole pattern rather than count agreeable results

<MCQ
  client:visible
  pretest

  options={[
    { text: 'Exporter only is proved and the formatter is cleared.' },
    { text: 'Exporter only and both remain compatible; the formatter isolation still matters.', correct: true },
    { text: 'Nothing was learned because your story was confirmed.' }
  ]}
  explanation="The result distinguishes candidates, but it does not distinguish exporter only from both. A useful result can narrow a set without selecting one unique explanation."

Here is the complete invented run. Both trusted controls preserve the hyphen. The two isolation paths each lose it.

| Recorded path | Observed output | Observation |
|---|---|---|
| Ordinary path | ABCD | Lost |
| Trusted control before isolation | AB-CD | Kept |
| Exporter isolation | ABCD | Lost |
| Formatter isolation | ABCD | Lost |
| Trusted control after isolation | AB-CD | Kept |

Work through the exclusions. The ordinary path conflicts with “neither”. Exporter isolation conflicts with “formatter only”. Formatter isolation conflicts with “exporter only”. “Both” predicts the full pattern and is the only compatible candidate **within the stated model and valid setup**.

This is not a vote where whichever hypothesis collects the most agreeable anecdotes wins. “Exporter only” matches several rows but has a contradiction in a valid isolation. Nor does rejecting it automatically prove “formatter only”: that model has its own contradiction. The combined-cause candidate is necessary to represent what these results support.

John Platt's “strong inference” calls for explicit alternatives, experiments with separating outcomes and further tests of what remains. Our small decision tree illustrates that procedure; it does not establish Platt's broader claims about scientific progress. [Platt's original argument](https://pages.cs.wisc.edu/~markhill/science64_strong_inference.pdf)

### Limits of the elimination step

The clean exclusions use the model's error-free, stable mechanisms and valid substitutions. In a noisy setting, a surprising result can arise without making a proposed explanation impossible. Measurement error, changing conditions and probabilistic predictions need an uncertainty assessment. A single contradiction does not carry the same force in every task. Klayman and Ha discuss this distinction explicitly; do not export the toy system's certainty into an unexamined real case.

## Separate repairing a cause from erasing the symptom

<MCQ
  client:visible
  pretest
  question="Both stages have the deletion setting active. The exporter setting is repaired, but the formatter remains unchanged. What should the ordinary path do?"
  options={[
    { text: 'Lose the hyphen, because the remaining formatter still deletes it.', correct: true },
    { text: 'Preserve the hyphen, because finding one cause removes every cause.' },
    { text: 'Prove that the exporter was never involved.' }
  ]}
  explanation="With two deletion stages in series, either active setting can produce the final symptom. A remaining symptom does not by itself show that the first repair changed nothing at its own stage."
/>

The team initially wanted to pick the guilty stage and declare victory. The matrix instead predicts a practical complication: fixing one active stage leaves the other able to remove the hyphen.

| Exporter setting after intervention | Formatter setting after intervention | Predicted ordinary-path output |
|---|---|---|
| Active | Active | ABCD |
| Off | Active | ABCD |
| Active | Off | ABCD |
| Off | Off | AB-CD |

Verify a repair in its isolated path and then retest the ordinary path. For this constructed run, disabling the exporter setting makes exporter isolation preserve AB-CD, but the ordinary path still produces ABCD until the formatter setting is also disabled. That persistence was predicted by “both”; it is not permission to edit the original results or exonerate the exporter after the fact.

### What to claim after the repair

Record which settings changed, which paths were retested and which inputs were used. A fresh label such as **JK-LM**, kept out of the diagnosis, can test the repaired system's prediction on another input. Passing that check supports the tested domain; it does not validate every possible label, character set or configuration. Keep the conclusion as specific as the evidence.

Here is an independent fictional case. A newsletter's **exporter** may remove accents, its **renderer** may remove accents, both may do so, or neither may. An inactive stage preserves its input. Trusted substitutes preserve accents exactly; the settings and readout remain stable. The input is **CAFÉ**. These are the new observations:

| Path | Observed output |
|---|---|
| Current exporter and trusted renderer | CAFE |
| Trusted exporter and current renderer | CAFÉ |
| Trusted exporter and trusted renderer | CAFÉ |

Before opening the solution, identify the compatible candidate and predict the ordinary path. Then say what would happen if only the renderer were replaced while the exporter remained current.

### When the procedure needs more work

Real cases may have interacting causes, imperfect measurements or more mechanisms than the list includes. A trusted substitute may also change timing, data or other conditions, so it may fail to isolate the intended cause. Write those limitations down and design checks for them. Do not assign numerical confidence from the number of models that survived: “one of four” here is a logical candidate count, not a probability calculation.
